# ASR 关键词上下文验证

## 行为

使用 jieba 0.42.1 自带词典和普通 `posseg` 标注（HMM 开启），不加载自定义词典。
正常完整 Thinker 回复在 Actor 接受后触发一次后台提取；普通和双流 TTS 均走此路径。
只分析回复末尾最多 2048 字符，保留人名、地名、机构名和其他专名，按原文顺序去重。
排除单字、纯数字、标点；默认最多 12 个词，空格拼接后最多 128 字符，不截断单词。

网关启动时以 `spawn` 创建共享的常驻进程池，默认 2 个子进程，可通过
`RTVA_ASR_CONTEXT_WORKERS` 配置（1～32）。每个子进程加载并预热一份 jieba 内置词典，
全部预热完成才接受请求；不复制网关已有的 Torch/ONNX 线程或网络客户端。
分词计算仅在子进程中执行，各进程拥有独立 GIL，可多核并行。
最多 32 个等待任务在 asyncio 中排队，只传递有界文本和截止时间，不传会话状态。
结果预算默认 100 ms，包含排队、进程通信、计算和结果返回；超时、队列满或失败不重试。
任务超时或会话取消不会提前释放仍在运行的进程容量；网关关闭时等待计算结束并回收进程。
预热启动预算为 60 秒。预热失败、超时或启动被取消时使用有界强制清理：先终止该池的
子进程，统一等待最多 1 秒；仍未退出则强制杀死并统一等待最多 1 秒，管理线程最多再等
1 秒。不会因某个初始化卡住的子进程而重新进入无限期的优雅等待，也不影响其他服务进程。
终止、强杀和回收都在调用 executor 的 `shutdown` 之前完成，避免异常退出的管理线程
持有关闭锁时阻止强杀；管理线程在期限内未退出则记录结构化告警，不再获取其关闭锁。
正常关闭仍优雅等待，单次提取的 100 ms 预算和 ASR 只读缓存行为不变。

ASR 直接读取最近一条正常完整、未中断回复的缓存，无现场计算或等待。
该轮缓存未就绪、为空或失败时不复用更早的话题，也不发送回复全文。
会话、轮次、生成代次、中断状态及结果期限均校验，断连取消后台等待。
关键词文本不记录到日志或指标；仅记录状态、数量、字符数、来源轮次和耗时。

## 宿主性能数据

预热后每种文本运行 100 次，2026-10-13 单独基准的 P95：

| 输入 | 字符数 | 计算 P95 |
|---|---:|---:|
| 短回复 | 16 | 0.115 ms |
| 中等回复 | 190 | 0.611 ms |
| 长回复（仅处理尾部 2048 字符） | 3248 | 3.448 ms |
| 陌生姓名密集文本 | 175 | 3.650 ms |

初始 20 ms 预算下，30 会话同时提交中等回复，重复 10 轮、共 300 次：

- 缓存读取 P95：0.006 ms，P99：0.008 ms。
- 事件循环 1 ms 定时器的额外延迟 P95：1.460 ms，P99：1.860 ms。
- 后台提取总耗时 P95：21.351 ms；157 次成功，143 次超时后丢弃。

配置的预算是结果有效时间，并非操作系统调度的硬实时保证。突发并发时可能超过该时间
才处理超时通知，但 ASR 不等待这条链路；到达期限后即使计算完成也不再缓存。
这些是合成负载数据，不包含真实语音、线上 ASR/TTS 时延或准确率评估。
无用户词典的首版仍可能漏掉陌生姓名、昵称和领域专名。

### 20 ms 与 50 ms 预算对比

同一宿主环境、2 个工作线程，分别对普通 190 字回复及陌生姓名密集的 175 字文本
做 15 轮 30 任务同时提交；每个输入和预算组合各 450 次。每轮结束后等待仍在运行的
超时计算真正结束，避免影响下一轮。

| 输入 | 预算 | 及时成功 / 超时 | 成功率 | 后台总耗时 P95 | 事件循环延迟 P95 / P99 |
|---|---:|---:|---:|---:|---:|
| 普通回复 | 20 ms | 224 / 226 | 49.8% | 21.257 ms | 1.498 / 1.896 ms |
| 普通回复 | 50 ms | 450 / 0 | 100% | 36.865 ms | 1.487 / 1.906 ms |
| 陌生姓名密集 | 20 ms | 0 / 450 | 0% | 31.869 ms | 5.834 / 15.484 ms |
| 陌生姓名密集 | 50 ms | 42 / 408 | 9.3% | 65.635 ms | 11.262 / 15.491 ms |

50 ms 下缓存读取 P95：普通回复 0.007 ms、陌生姓名密集文本 0.006 ms。
成功表示提取结果在期限内返回且有关键词，不表示实体识别正确或 ASR 准确率提升。
该轮验证将默认预算改为 50 ms：普通回复的突发命中率明显改善，陌生姓名密集负载仍有瓶颈。
延长预算不会让计算更快，也不会让 ASR 等待 50 ms；结果未就绪时 ASR 仍使用空 context。
后台超时通知可能受事件循环调度影响而晚于期限，但过期结果不缓存。

复现命令：

```bash
PYTHONPATH=src uv run python scripts/benchmark_asr_keywords.py --budgets-ms 20 50 --rounds 15
```

### 常驻 2 进程、100 ms 预算验证（2026-10-14）

使用网关虚拟环境，在宿主运行离线基准；机器可见 96 个逻辑 CPU。
以 `spawn` 创建 2 个常驻进程，各自加载和预热词典，启动阶段约 1.4 秒，
不计入每次请求预算。只有子进程导入 jieba 并执行分词；网关只发送文本、截止时间并接收结果。
测试确认两个不同于网关 PID 的进程已完成预热，Python 计算区间可以重叠，
多次请求复用同一批进程，正常关闭及后续模型启动失败均会回收进程。

30 任务同时到达，每种输入重复 15 轮、各 450 次；复测结果：

| 输入 | 及时成功 / 超时 | 成功率 | 提取总耗时 P95 / P99 | 事件循环额外延迟 P99 |
|---|---:|---:|---:|---:|
| 普通回复（190 字） | 450 / 0 | 100% | 27.814 / 31.406 ms | 1.049 ms |
| 陌生姓名密集（175 字） | 443 / 7 | 98.4% | 85.396 / 102.943 ms | 1.082 ms |
| 长回复（3248 字，仅分析末尾 2048 字） | 450 / 0 | 100% | 74.965 / 80.957 ms | 1.084 ms |

总耗时包括排队、进程通信、计算及结果回传，不是单次分词 CPU 时间。
同一天首轮普通回复、陌生姓名密集文本均为 450 / 0；两轮结果说明存在系统调度波动，
不能将首轮的零超时当作稳定保证。历史线程数据不是同轮对照，不据此计算加速倍数。
超时通知可能晚于 100 ms，但超过有效期限的结果不会缓存，ASR 仍不等待提取。

另做 60 任务突发、每种文本 15 轮（各 900 次）的容量压力测试：三类输入均为
510 次成功、390 次立即 `overloaded`、0 次超时。默认只容纳 2 个运行任务和 32 个等待任务，
因此每轮接受 34 个、拒绝 26 个，不会无限排队；这不是全部 60 个任务都提取成功。
此时三类输入的事件循环额外延迟 P99 为 1.096 / 1.040 / 1.032 ms。
这些基准不包含真实 VAD、模型推理或网络负载，也不代表任意文本/负载都不会超时。

```bash
PYTHONPATH=src .venv/bin/python scripts/benchmark_asr_keywords.py --workers 2 --concurrency 30 --budgets-ms 100 --rounds 15
PYTHONPATH=src .venv/bin/python scripts/benchmark_asr_keywords.py --workers 2 --concurrency 60 --budgets-ms 100 --rounds 15
```
